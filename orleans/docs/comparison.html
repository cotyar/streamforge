Plan 005 · Dapr sibling runtime

Orleans vs Dapr

Same platform, two runtimes. StreamForge's SQL engine, contracts, application logic, REST/SignalR API, and console SPA (~70% of the codebase) are shared verbatim between an in-process Microsoft Orleans silo and a sidecar'd Dapr deployment — only the actor/grain runtime and the transport underneath differ. This page is the honest answer to "why Orleans and not Dapr, or vice versa": measured latency, delivery-semantics tradeoffs, and the decision matrix for which building blocks fit which constraints.

Executive summary

Architecturally, Orleans should win on raw latency — in-process grain calls and in-memory streams put the whole pipeline inside one process with no serialization or network hop between stages — and Dapr should trade that latency for reach: any sidecar'd process in any language can publish into or subscribe out of the platform's pub/sub topics, with building blocks (actors, pub/sub, state store) that map directly onto k8s-native primitives an ops team already runs. What this wave actually measured contradicts the latency half of that story: the Orleans flavor's primary tableDelta SignalR relay turned out to be live-broken (zero samples — see Measured latency), and a supplementary measurement that did work showed Dapr faster, not slower. Typed single-runtime performance and polyglot reach remain the two poles worth choosing between — but read the latency row below as "what we found," not "what the architecture diagrams predict." Neither runtime is "better" in the abstract — the table is the actual decision function.

Architecture side-by-side

Both flavors compile the identical streaming SQL via the identical StreamForge.Engine, seed the identical demo world (SeedCatalog), and serve the identical REST/SignalR contract (shared/StreamForge.Api) — see the reuse scorecard. What differs is everything below that surface: how an entity's state and timers are hosted, and how events move between entities.

Structurally, Orleans' path is function calls inside one process; Dapr's path is app → sidecar → Redis → sidecar → app, repeated at every stage boundary (decision D-D: fixed envelope topics, since per-entity topics can't be subscribed without a restart). That structural difference is the intuitive explanation for why Dapr should be slower — see Measured latency for what this wave actually found, which does not confirm that intuition.

Measured latency

Methodology. Same seeded table (order_states — SELECT order_id, symbol, side, stage, stage_rank, stage_ts, qty, filled_qty, px FROM order_events LATEST BY (order_id)), same machine, same clock (no skew to correct for), one runtime at a time (never concurrently, so both get the full machine's CPU). A bun script (tools/bench/latency.ts) subscribes the SignalR tableDelta event over /hubs/stream and, for every ASSERT row (Z-set weight +1 — the RETRACT half of each LATEST BY update is skipped, or every measurement would be doubled), computes latency_ms = client wall clock at delta arrival − row.stage_ts. stage_ts is confirmed as the source event's own generation timestamp by reading the generator profile: shared/StreamForge.AppCore/Generators/MarketDataProfiles.cs sets evt["stage_ts"] = evt[EventRecord.TimestampField] — i.e. it's copied verbatim from _ts, itself stamped with DateTimeOffset.UtcNow at the exact moment the synthetic event is generated. The number is therefore genuinely end-to-end: generation → ingress → the table's LATEST BY operator → delta publish → SignalR relay → this script's handler. First 10 seconds of each run are discarded as warmup, and any row whose stage_ts predates the run's own start is discarded (a backlog/rebuild artifact, not steady-state latency). Each run collects ≥500 samples or runs 90 seconds, whichever comes first. Orchestrated end-to-end by tools/bench/run-bench.sh: fresh isolated Orleans instance (temp --DataDir, ports 6199/6299) → run → full teardown → dapr/tools/reset.sh + dapr/tools/run.sh (5399/3599/4599) → run → full teardown.

The primary measurement hit a live bug — reported here, not fixed (out of this wave's scope). Running this benchmark against a freshly booted Orleans instance found that its SignalR tableDelta relay (and, observed the same session, pipelineResult) never delivers to a subscribed client: zero events over repeated 15–90s windows across three different seeded tables (order_states, positions, leg_exposure), while the same tables' REST /api/tables/{id}/metrics shows deltasIn/deltasOut growing continuously the whole time, and a real browser against the same instance shows rows never updating live. sourceEvent and pipelineMetrics (both single-object SignalR arguments, vs. tableDelta/pipelineResult's List<T>-of-DTO arguments) work correctly in the same session — see dapr/ARCHITECTURE.md's "Known live bug" section for the full repro. The honest surprise: Dapr measured FASTER on both signals actually collected, contradicting this plan's own a-priori assumption. The plan going in expected Orleans to win on latency by a wide margin (in-process grain calls, no sidecar hops) and Dapr to lose 10–40× to batching cadence and sidecar round-trips. That is not what was measured. Dapr's real tableDelta path — generator batch tick → publish → Redis → deliver → TableActor (itself a sidecar round-trip even for the actor invocation, per ActorProxyOptions.UseJsonSerialization) → publish → Redis → deliver → SignalR — came in at a real p50 of 7 ms on localhost; Dapr's sourceEvent path (generator batch tick → publish → Redis → deliver → SignalR, one fewer hop) at p50 2 ms. Orleans' sourceEvent path — supposedly the simplest possible hop, a grain timer pushing straight into an in-process stream a hosted service already holds a subscription on — measured p50 60 ms, roughly 30× slower than Dapr's equivalent hop. This wave did not root-cause that gap (out of scope — report, don't fix), but two honest observations: (1) stage_ts/_ts is stamped at the moment the generator code actually runs, so batching-induced "held event" time is invisible to this metric on the Dapr side by construction — it isn't that Dapr's batching cost nothing, it's that this metric can't see it, since the timestamp itself is stamped after any batching delay already happened; (2) the Orleans number may reflect grain-timer scheduling granularity and/or turn-based dispatch contention on this specific single-silo local topology rather than an inherent property of in-process actor systems — a plausible starting point for whoever investigates the tableDelta bug next, since both symptoms live in the same StreamBridgeService/grain-timer machinery. The honest conclusion this wave can support: real numbers, on this benchmark, on this machine, showed Dapr at least as fast as Orleans and the Orleans path measurably slower where it could be measured at all — which is the opposite of this plan's working assumption, and exactly why "run it for real" beats "assume the architecture diagram tells you the answer."

Delivery semantics

Orleans memory streams

In-process, single-silo delivery — effectively exactly-once within a silo lifetime: a stream push is a direct in-memory handoff to the subscribing grain, no broker, no redelivery mechanism to misfire. The tradeoff is the flip side of the same coin: it's a .NET-internal transport (the closed door the Dapr flavor's polyglot pub/sub opens) and doesn't survive a full silo restart mid-stream (no durable log to replay from — grain state persistence is separate from stream delivery).

Dapr pub/sub, at-least-once

Redis pub/sub is at-least-once by nature — a message can be redelivered (network blip, subscriber restart mid-processing, sidecar retry). This is the transport's honest nature, not papered over here: dapr/POLYGLOT.md documents that every ingress endpoint always returns 200 OK even on a malformed payload specifically because a non-2xx response is Dapr's redelivery trigger — an unconditional 200 avoids a poison message looping forever, but it also means the app itself, not the transport, is the only thing standing between "delivered twice" and "processed twice."

The idempotency gap — thought through honestly, not glossed over. A redelivered sf-table-delta envelope would double-apply its Z-set deltas: a retract(−1)/assert(+1) pair replayed a second time doesn't cancel out (Z-set weights aren't idempotent against replay — they're only correct under exactly-once application of each delta). Concretely: a duplicate delivery of a positions delta would apply the same quantity retraction/assertion twice, corrupting the running aggregate. Today this is mitigated only by Redis pub/sub's happy-path behavior (in practice, redelivery is rare absent an actual failure/restart mid-delivery) — there is no explicit dedup/idempotency key on any envelope in this plan. This is flagged here as a real production consideration for anyone taking the Dapr flavor further, not a solved problem: a production hardening pass would need per-envelope sequence-based dedup (the envelopes already carry monotonic seq fields that a consumer-side "last applied seq" check could use) before this flavor should sit in front of anything that can't tolerate an occasional double-applied delta.

Polyglot processing

The Orleans flavor's only door for a non-.NET participant is the typed-gRPC client path — consume-only, and the client itself is .NET-toolchain-generated even though the wire format (proto3) is language-neutral. The Dapr flavor's pub/sub topics are the actual door: sf-sources is a plain HTTP/gRPC publish to the sidecar, JSON body, no .NET-specific serialization anywhere on the wire (dapr/POLYGLOT.md is the frozen contract). Three working processors prove this isn't theoretical:

Python — enricher

dapr/processors/python-enricher (~240 lines): subscribes sf-source-trades via its own sidecar, derives an enriched view, registers and publishes a brand-new source back into sf-sources — the derived source shows up in the console exactly like any seeded one.

TypeScript — bun consumer

dapr/processors/ts-consumer (~180 lines): subscribes sf-table-delta/sf-pipeline-out directly — no .NET runtime anywhere in this process.

Java — consumer

dapr/processors/java-consumer (~260 lines): buildable sample (gradle/maven), proving the contract is genuinely runtime-agnostic, not "Dapr .NET SDK plus a Python special case."

What this unlocks in a client conversation: a Java/Kotlin risk-analytics team, a Python data-science team, and a TypeScript tooling team can each attach a processor to the same running platform without touching the .NET codebase or waiting on a .NET release — they read/write plain JSON over a documented topic contract with frozen envelope shapes (additive evolution only, exactly like every other DTO in this project).

Operational story

Orleans

  • Clustering & placement: Orleans' own membership/placement provider — a well-understood but Orleans-specific operational model (this demo runs localhost clustering; production multi-silo would swap clustering/stream/storage providers, per the docs' Limitations section).
  • Local dev footprint: dotnet run. One process, nothing else to install or start.
  • State: one JSON file per grain under data/ — human-readable, rm -rf data/ to reseed.

Dapr

  • Sidecar + placement + scheduler: every instance runs with a Dapr sidecar; actor placement and reminders/timers are separate k8s-shaped services (dapr_placement, dapr_scheduler containers in local dev) — building blocks an ops team running Kubernetes already has patterns for.
  • Local dev footprint: dapr init (Redis + placement + scheduler containers) once, then dapr/tools/run.sh — heavier first-time setup, same one-command inner loop after.
  • State: Redis (state.redis, actorStateStore: true, keyPrefix: appid scoping) — dapr/tools/reset.sh SCANs and deletes this app's keys to reseed, the Dapr-flavor equivalent of deleting the Orleans data/ directory.

Ports, for anyone reproducing this: Orleans owns 5199 (REST/SignalR/SPA) + 5299 (gRPC); Dapr owns app 5399, gRPC reserved 5499 (not yet serving), sidecar HTTP 3599 / gRPC 4599. The two flavors never share a port and can run side by side on one machine, which is exactly how this page's benchmark was produced (sequentially, not concurrently, for CPU fairness).
